# Documentation rules

Before creating or editing documentation, read and follow the
[contributor guide](README.md), including its Diataxis authoring rules.

For end-user pages, treat minimalism, plain prose, and simplicity as requirements
without losing the precise semantics needed for accuracy and clarity. Ask whether
each section and detail helps the reader act, understand, or decide. Trim what does
not, and tell the requester when requested content conflicts with this standard.
Include current status, known gaps, and forward-looking plans when they help
readers understand what is available or planned. Omit historical process/status
notes, drafting decisions, and writing artifacts that only recount how the
documentation evolved. Include implementation details only when they help end users.

Check each remaining section against its Diataxis type: Tutorial, How-to,
Explanation, or Reference. Move substantial material serving another purpose to
the matching page, or use a concise accordion when relevant details would interrupt
the page and do not warrant a separate page, such as example output, a focused
explanation, or troubleshooting for a specific step.
